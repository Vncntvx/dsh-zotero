## 3. 重要问题详细说明

### I1. 写审批缺 agent 时 fail-open

**位置**：`src/write-approval.ts:115-119`

```ts
const approval = ctx.get('approval')
// Absent approval service: ... Absent agent: ...
if (approval === undefined || exec.agent === undefined) return 'allowed'
```

**问题**：`approval === undefined`（无审批服务）与 `exec.agent === undefined`（无 agent）被合并成同一个「跳过」分支。当**有审批服务但缺 agent** 时直接返回 `'allowed'`，绕过 `approval/policy: never`。

**矛盾**：

- 同文件模块头 settlement map（21-22 行）写明：`unavailable` / no agent / infrastructure failure → fail closed
- harness `serviceAsk`（`packages/core/tools/src/index.ts:1738-1742`）对无 agent 一律 `deny`
- sandbox 升权（`packages/sandbox/sandbox/src/escalation.ts:132`）同样 fail closed

**影响**：非 tool 调用者手搓 `ZoteroWriteCall` 漏传 agent 即可跳过策略闸门。测试 `write-approval-policy.spec.ts:61-80` 已固化现状（mock 了会 reject 的 approval，仍断言 `allowed`）。

**建议**：拆开两条件——`approval === undefined` 保持 skip；`exec.agent === undefined` 返回 `'unavailable'`。同步修正测试。

**依据**：`packages/core/tools/src/index.ts:1738-1742`；`packages/sandbox/sandbox/src/escalation.ts:132`。

---

### I2. 共享连通性提问被首个调用方 abort 连坐

**位置**：`src/ask.ts:200-214`、`src/ask.ts:157-167`

**问题**：`ConnectivityRecovery` 按失败码去重并发提问，但共享 question 的 `signal` 绑定**首个调用方**的 `exec.signal`。该调用方一旦取消（agent 中断/超时/会话关闭），`questions.ask` 以 `ASK_ABORTED` 拒绝，所有等待者一起失败。其余调用方的 `exec.signal.aborted` 为 false，会抛出**原始 ZoteroError**——完全没得到提问机会。

**建议**：共享提问改用 gate 自有 `AbortController`，或沿用本仓库 `awaitSharedOperation` 的「最后一个等待者离开才 abort」语义（`src/concurrency.ts:94-131`）。

**依据**：`packages/interaction/user-questions/src/types.ts:70-77`（signal 是 pending request 的取消生命周期）；`src/concurrency.ts:94-131`（本仓库自己的正确形态）。

---

### I3. `errnoCodeOf` 被 domain code 遮蔽（潜伏）

**位置**：`src/errors.ts:282-296`

**问题**：文档写「the Errno-style code of an error's cause chain」，实现是 BFS 返回**第一个**带字符串 `code` 的节点。`HarnessError`/`ZoteroError` 自身就带 `code: 'ZOTERO_TIMEOUT'` 等 domain 码，会遮蔽真正的 errno 码。

当前两个调用点恰好安全（裸 fetch 错误 / fs `access` 错误），但 `errnoCodeOf` 是随 `index.ts` 导出的公共 API。

**建议**：跳过 `HarnessError` 实例自身的 `code` 继续走 cause，或只接受 `E*`/`UND_*` 形态。

**依据**：`packages/llm/llm/src/error.ts:13-21`；`tests/unit/errors.spec.ts:41-80`（未覆盖「自身带 code + cause 带 code」）。

---

### I4. `waitOrPromote` 在 `registry.start` 拒绝时无前台回退

**位置**：`src/job-runner.ts:336`

```ts
const { id, done } = this.start(wrappedTask) // 无 try/catch
```

**问题**：`JobRegistry.start` 在「无 job controller 服务该 owner」等条件下会 throw（`packages/jobs/jobs-local/src/index.ts:209`）。tool-bash 的官方模式是 catch 后回退前台（`packages/shell/tool-bash/src/index.ts:514-522`），dsh-zotero 的 promote 路径直接让整个工具调用失败。

**建议**：`waitOrPromote` 对 `this.start` 加 try/catch，失败时回退 `task.run(...)` 前台执行并 log warn（与 tool-bash 同形）。显式 `run_in_background` 路径保持 throw（用户明确要后台）。

**依据**：`packages/shell/tool-bash/src/index.ts:514-522`；`packages/jobs/jobs-local/src/index.ts:209`。

---

### I5. BibTeX 条目切分把条目间注释算进 `entry.text`

**位置**：`src/export-mapping.ts:108-133, 200-216`

**问题**：`splitBibtexEntries` 用「下一个 `@type{` 起点」作为上一条目的 `end`，条目之间的 `%` 行注释被算进上一条的 `BatchEntry.text`。`locateExportItems` 的 BibTeX 配对是全文等值比较（`normalizeBibtexEntry` 只剥 `@type{key,` 前缀，不剥尾随注释），单条目导出体与 batch 体不再相等 → 该条目丢失 `key/start/end`（UI 降级为「无法定位」）。

**建议**：`BatchEntry.end` 改用 `entryEndOf` 算出的闭括号位置，或比较前截到闭括号。

**依据**：现有测试只钉了空行尾随（`tests/unit/export-mapping.spec.ts:16-35`），未覆盖 `%` 注释尾随。

---

### I6. `resolveNamed` 不校验响应 key 一致性

**位置**：`src/local/scope-directory.ts:270-289`

**问题**：ref 形参解析时直接用 `entry.key` 重建 ref，不校验 `entry.key === ref.key`。异常响应会静默改指向。写域 `readItem`（`write-domain.ts:211-215`）有此检查，读路径不一致。

**建议**：增加 `if (entry.key !== ref.key) throw new ZoteroError(..., ZOTERO_UNEXPECTED)`。

**依据**：`docs/defensive-patterns.md`「Honor public contracts on BOTH sides」；`write-domain.ts:211-215`。

---

### I7. 空页 `nextOffset` 原地踏步

**位置**：`src/local/search-domain.ts:95`、`src/local/pagination.ts:34-39`

**问题**：

1. 非数组体静默当作空数组：`const rows = Array.isArray(json) ? json : []`
2. `nextOffsetOf(offset, 0, total)` 在 `total > offset` 时返回 `offset`，调用方按 `nextOffset` 翻页会死循环

**建议**（择一，fail-loud 更符合本仓库风格）：

- `returned === 0 && offset < total` 时抛 `ZOTERO_UNEXPECTED`；或
- `nextOffsetOf` 在 `returnedCount === 0` 时返回 `undefined`
- 同时 `Array.isArray(json) === false` 应 fail-loud

**依据**：`docs/defensive-patterns.md`「Report orthogonal outcomes independently」；本仓库 changes 域对形状不合约记 `unreadable` 而非「没有变化」。

## 4. 各审阅目标结论

### 4.1 最优实现与官方范式对齐

**总体：高度对齐。**

- 11 个工具全部走官方 `defineTool` + `ctx.tools.register`，schema DSL、canonical 输出 + `output.render` 分离、纯 presentation 钩子均合规
- Service 类形态（`extends Service` + `static inject` / `static Config` / `declare module` 合并）与官方一致
- Schemastery 全字段 `.volatile()` 满足 settings 面硬性要求
- Typert 手写 manifest + contract 共享 endpoint 身份正确；「不导出 `./typert` + 自注册」避免双注册
- 写审批用的是官方 seam（`ctx.approval.request` + `userQuestions.ask` 的 `plan-review` intent），不是自制审批
- shell 写探测器在 `tools/pre-execute` 上正确 `next()` 委托

**偏离点**：

- CSS 层整体未对齐 `--dsw-alias-*` / `--dsw-radius-*` / 0.5px 发丝线 / `corner-shape: round`（见样式契约簇）
- job-runner promote 路径与 tool-bash 的 start 失败回退模式不一致（I4）
- `dsh.harnessRange` 是插件自造字段，harness 不读取（A4）

### 4.2 冗余与死代码

- **未使用导入/变量**：host 16 处、client 4 处、test 4 处（`tsc --noUnusedLocals` 实测，见 A1）
- **死函数**：`sameIncludes`（A2）
- **死导出**：`isSchemaComplete`、`assertResolvedConfig`（A10）
- **注释过时**：dev-lib.cordis.yml 工具数、test-lint.mjs 文件数（A24/A25）
- **无遗留调试代码**：仅 client 挂载失败时的 `console.error`（有意的「Fail visible」）

### 4.3 错误与隐患

- **类型安全**：`strict: true`；`any` 滥用未发现；少量非空断言均有前置收窄
- **异步处理**：共享 promise 的 `void .catch(() => undefined)` 是正确模式（防止 unhandled rejection）；无浮动 promise
- **错误处理**：`ZoteroError extends HarnessError` 带稳定 code；abort 统一映射 `TOOL_ABORTED`
- **安全**：loopback-only 由 `resolveConfig` 把关；`redirect: 'manual'`；note-format 全量 escape 后再规则；密钥不落日志/配置
- **已知隐患**：I1（fail-open）、I2（信号连坐）、I3（errno 遮蔽）

### 4.4 偏离官方范式

- 大部分 API 使用正确（`defineTool`、`ctx.approval`、`ctx.jobs`、`dsh-timeout` 的 `deadline`/`timeoutOf`、`HarnessError`）
- 未发现「重复造轮子」：`json.ts` 是对 harness `isJsonValue` 的合理封装扩展
- `mountedNamespace()` 的 `ctx.reflect.get('remote.zotero')` 是**有意偏离**（自供 namespace 无法用 `ctx.remote.<ns>`），已文档化

### 4.5 整体一致性与可维护性

- 模块边界清晰（host / local domain / tools / client / scripts 分层）
- 依赖单向：client 只依赖 contract/settings-namespace/json 等纯表面
- client-graph 权威门禁健全（resolve 拒绝 + metafile 复查 + handoff 自检）
- pin 一致性检查通过；coverage ratchets 贴近当前实测
- **无过度设计**；配置面完整（可调项均进 Config）
