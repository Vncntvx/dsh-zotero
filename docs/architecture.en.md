# System Architecture

This page describes the system by runtime concern: component topology, data flows, state and consistency, concurrency and resources, security boundaries, client-host contracts, and design boundaries. Each invariant names its current implementation and verification. Configuration fields, tool parameters, and interface presentation belong to `configuration.md`, `tools.md`, and `features.md`; upstream workaround patches belong to `development-notes.md`. The page is organized by responsibility, not by source directory.

## Component Topology and Lifecycle

### Components and Dependency Direction

| Component               | Cordis key                                | Settings namespace | Default | Responsibility                                           |
| ----------------------- | ----------------------------------------- | ------------------ | ------- | -------------------------------------------------------- |
| `dsh-zotero`            | `zotero` (wire namespace `zotero`)        | `zotero`           | on      | Connection, model tools, literature trail, settings page |
| `dsh-zotero/library`    | `zoteroLibrary` (wire namespace `zotero`) | `library`          | on      | Library panel host endpoints and right-sidebar interface |
| `dsh-zotero/reader`     | `reader` (wire namespace `zotero`)        | `reader`           | off     | Research Reader tab and reading endpoints                |
| `dsh-zotero/scholarly`  | `scholarly`                               | `scholarly`        | off     | External scholarly index retrieval and fulltext reads    |
| `dsh-zotero/enrichment` | `enrichment`                              | `enrichment`       | off     | Explicit parsing, artifact lookup, local semantic models |

The core holds the data plane and agent capabilities. Library forwards local-library endpoints to core, Reader reuses core reads and writes, scholarly authorizes external retrieval, and enrichment is the document parsing component that provides read-only artifact lookup and explicit parsing. These four components depend on core. Core reaches enhancement through the `FulltextEnhancer` and `EvidenceRanker` slots. `FulltextEnhancer` exposes read-only `lookup` for source Markdown and `lookupArtifact` for opaque artifact IDs.

### Mount, Configuration, and Unmount

The loader mounts the default-exported `ZoteroService` with validated configuration. The plugin accesses the network per request and makes no external or local request while loading. A structural configuration change rebuilds the HTTP client, provider, and write-tool set on the existing instance when one of the six `TRANSPORT_CONFIG_KEYS` changes (`baseUrl`, `timeoutMs`, `maxResponseBytes`, `maxInFlightRequests`, `writeAuthorizeDeadlineMs`, `writeEnabled`); other limits are read live by the provider and do not rebuild.

Unmount withdraws slots, stops new admission, terminates the parse and download jobs the component started, and waits for cleanup; admitted foreground read scopes drain and then release. Local terminal children use the upstream `scrubbedParentEnv()`: after removing credential-shaped values and `DSH_*`, it restores the host proxy variables so a child uses the same network path as the host. An explicitly supplied environment table follows the same rule but receives no proxy variables.

### Host Contract Adapters

`ctx.zotero` is the core service boundary; Typert services and wire endpoints are described under "Client-Host Contracts." Mirrors, private routes, and control adapters that depend on a specific pin are not described here: they are upstream patches in `development-notes.md`, which owns their cause and exit condition.

## Data Flow

### Local Reads

The panel calls browse, collectionPath, search, item, childPage, and export through `ctx.zoteroLibrary`; `useLibraryFeed` coalesces identical requests, applies short TTL caches keyed by `serverId`, and caches only successful reads. Model tools read search results, items, attachments, annotations, notes, and context through the provider; scope names and item-type vocabulary come from local cache directories; `trash` belongs only to the panel and is absent from model tool schemas.

Reader details resolve the parent from the attachment returned by Zotero and carry the verified library and server identity into the parent read. Reader calls core for the parent and bounded children, including when Library is disabled. Attachments and notes page independently. Loaded note rows stay available for batch selection until a note mutation refreshes the list. Sibling PDF links use a fresh local file resolution and retain their own reading state and geometry. `tests/host/reader-details.spec.ts` checks group library reads, child offsets and the session access gate. `tests/client/reader/ReaderDetails.spec.tsx` checks batch citations across note pages.

Reader checks session access before fetching a page of native annotations for a Zotero attachment. The response retains the attachment's library and instance, the annotation versions, and any validated PDF geometry. The endpoint advertises annotation writes only for the personal library with writes enabled in core. `tests/host/reader-annotations.spec.ts` verifies pagination, geometry, identity, and access denial against a scripted Local API.

Reader publishes bounded reading history in the browser. It rejects serialized records over 1,000,000 UTF-16 code units before parsing entries. Only attachment refs with a server qualifier enter the history snapshot, so legacy refs without instance identity cannot restore across libraries. When present, the parent item ref must belong to the same server and library, so the Library list cannot attribute reading time to the wrong source. Recently read links stay within the current server-qualified library and resolve the attachment again. Position restoration also requires the file fingerprint to match. The Library list consumes the same snapshot and uses the verified parent ref for Last read. Reader counts time while both the Harness tab and the browser page are visible. Disabling reading-state persistence hides the snapshot and stops saving. `tests/client/reader/reading-history.spec.ts`, `tests/client/reader/ReaderTab.history.spec.tsx`, and `tests/client/library/reading-visits.spec.tsx` cover storage, timing, and list updates.

Historical PDF citations are recovered from Composer quote blocks in the admitted user and steering messages of a completed turn. Reader resolves the exact qualified attachment ref again under current session access and loads the current bytes even when that attachment is already open. Page and geometry reuse require a matching SHA-256 of the complete PDF, computed before transfer to the PDF.js worker. Older fingerprints and browsers without Web Crypto can still open the attachment and show the version warning. The Reader navigation and citation tests cover permission revocation, a mismatched version, and an unavailable page.

Literature Trail uses the returned fulltext passage’s qualified attachment ref and preview for text location. Reader loads the current PDF under the session’s file access. For a MinerU passage, it first compares the artifact’s recorded SHA-256 with the current PDF. Reader scans at most 256 physical pages, with a 16,000 UTF-16 code-unit cap per page and a five-second deadline. The scan matches case-sensitive text with whitespace and common ligatures normalized. Only a complete scan can establish uniqueness. A unique match opens the page and paints a temporary PDF region when the rendered text layer supports it. Cross-page matches open at the first verified page, repeated matches offer their candidate pages, and incomplete or missing matches show their status. Navigation, dismissal and teardown cancel the scan. The client evidence specs verify attachment routing, matching, artifact versions, cancellation and stale results. The Chromium PDF smoke checks the overlay against the rendered glyphs.

Reader reads a selected note through a session-gated Remote and requests source HTML explicitly from core. Standalone note tabs identify a note by its canonical Zotero item ref and session. The tab checks note access independently of Workspace Files access and loads the Reader UI chunk on demand. The host verifies the item type before returning its contents. The response carries the note version and bounded plain text. The browser parses HTML in an inert template and recreates formatted content with a fixed set of elements and attributes. Links and external images stay inactive. An explicit image request checks note, attachment-resolution, and Workspace Files permissions, then reads a local raster attachment only when Zotero confirms the same instance, library, and parent note. Each read is capped at 2 MiB, and the note revokes its local image URL on close. The normal item and model-tool responses retain their plain-text note contract. `tests/host/reader-note.spec.ts` and `tests/client/reader/ReaderDetails.spec.tsx` cover the read and display boundaries.

Reader text attachment tabs resolve the exact qualified Zotero attachment again and require a supported local media type before reading a bounded Workspace Files byte window. The supported formats are HTML, XHTML, Markdown, and plain text. HTML is rebuilt without active content, and Markdown rendering runs without parent file or image resolvers and replaces all Markdown images before rendering. A prefix read can display text and cite the rendered range with a visible notice. Only a complete byte read can claim a content fingerprint.

PDF and parsed-document tabs exchange selected text only with a matching qualified attachment ref and complete SHA-256. The PDF action inspects the session-authorized cache for the exact attachment, then opens its opaque artifact ID. The parsed tab verifies the cache metadata again before searching the rendered blocks. The reverse action resolves the same attachment under the session's file permissions and uses the regular PDF evidence locator. Only unique matches can highlight a region or block. Cached geometry is read under the same prepared-document lease. The host verifies the content-list digest and accepts up to 240 flat rows or 256 KiB, with validated physical page indices and integer boxes on a 0–1000 scale. The UI can fall back to the recorded physical page if a box or known source orientation is unavailable. A PDF selection matches a single cache entry by page and overlap before the Markdown fallback runs. The artifact and browser suites cover invalid and missing boxes, ambiguous selections, and an upright figure round trip.

Quotes from parsed entries use the existing Composer quote card. They carry the artifact ID, entry kind, attachment ref, PDF SHA-256, physical page and optional normalized box. History validates the ref, hash and box before passing them to the same PDF evidence locator. Each region jump reads the current PDF again, including when its tab is already open. Without a validated box, Reader uses the recorded physical page. Quotes of selected Markdown text also store a bounded text prefix alongside the UTF-16 range. Highlighting requires that prefix to match the rendered range when present.

Closing a PDF capture preview cancels a pending jump to the corresponding parsed region. Losing cache access cancels pending jumps from both the preview and the PDF selection. A new PDF jump, a different parsed artifact, tab closure, or loss of attachment resolution or file access cancels a pending jump from the parsed document. Changing the selected passage cancels its pending lookup. The range is identified by its text, physical pages, and text offsets so repeat events for the same range leave the lookup active. After an explicit request, a capture can read MinerU text cached for the same attachment fingerprint. The host accepts one region per page within the 0–1000 coordinate space and quotes only text or heading blocks wholly contained by the capture. Cross-boundary blocks and pages without a matching block mark the result incomplete. The request reuses the committed cache digest and the existing session read grant, and it neither uploads the image nor submits a parse. The capture, selection, and parsed-document tests cover late responses, access revocation, and retry.

Reader model translation sends an explicitly submitted excerpt of at most 8,000 UTF-16 code units through the active session's selected Harness model. The host rechecks the session and access after preparing the adapter call. The one-shot request carries the selected text and translation instruction, uses a 30-second deadline and 4,096-token output cap, and returns only completed translation text. Browser translation results are cached in the Reader tab. Model translations use the session's current route on each request. The host and client Reader translation specs check the payload, remote access, explicit submission, and incomplete-output handling.

An annotation draft can explicitly request a model-suggested comment using the same excerpt boundary and session check. The host caps the response at 512 tokens and returns up to 1,000 UTF-16 code units. Reader displays the response separately until the user accepts it into the editable comment. Saving uses the original selection geometry and goes through the native annotation approval.

Read concurrency is bounded by `searchConcurrency` and `graphConcurrency`; candidate and attachment scans share the retrieval budget, which serializes at 1; batched get keeps one slot for interactive reads when transport capacity allows; note bodies are scanned on the first page only. Non-`citation` export formats return all items in one request (at most 50), `bibtex`/`biblatex` add one metadata batch, and `citation` batches by 50; the panel takes rendered text or citations only.

A tool schema's `default` is a JSON annotation that does not participate in validation; tool code applies defaults, and mutually exclusive combinations are checked by parameter presence (an omitted retrieve mode means `evidence`).

Lexical retrieval ranks with BM25 (k1=1.2, b=0.75) over each item's own passage corpus; the query side drops function words and duplicate terms, and zero-score passages never enter the lexical route. The `EvidenceRanker` slot swaps in a lexical-plus-semantic hybrid when enrichment's model is enabled; RRF only orders results. `search-text.ts` keeps mirroring Zotero's `normalizeForSearch`; `includeTrashed` never appears in retrieval tool schemas.

A fulltext read first looks for valid same-source Markdown; on a miss, local reads use Zotero `/fulltext`, and scholarly reads download an authorized PDF and extract its text. `complete=true` returns the whole bounded document or a spill handle; a window chain continues losslessly with `nextStart`/`continuation`, and a changed source or generation refuses continuation. An absent artifact or changed source stamp is a normal miss; permission, I/O, and corrupt-protocol failures are reported explicitly.

The literature trail folds session events incrementally, delivers list heads by window with exact aggregates computed before truncation (filter counts, passage totals, deduplicated export count, and an exact total per list). Lists cut by the window are paged back through the core `sourcePage`; every continuation must carry the previous `revision`, and a moved trail is refused with `ZOTERO_SOURCE_PAGE_STALE`. Evidence facts keep the attachment, match kind, and matched fields; only successful, structurally valid calls produce facts.

Claim links are reader-authored. Browser session storage holds at most 32 claims with 24 links each and a combined 256 Ki UTF-16 code-unit limit. Each link retains an excerpt, source and attachment references, and the available retrieval and position identifiers. Reader location uses a unique match in the current projection and the same verifier as the source inspector.

### Local Writes

Reader annotation edits carry the version shown in the editor. After approval, the domain reads the current object on the pinned instance, verifies the subtype and exact version, and includes that version in the PATCH body alongside the normal header. Reader refreshes the list on conflicts and leaves the next submission to the user. `tests/local/write/annotations.spec.ts` checks the Local API payload and stale version refusal.

Reader converts text-node rectangles through the PDF.js viewport and submits one native annotation per physical page. Missing page geometry or truncated selection text disables creation. The reviewed plan shows the exact page excerpts, color, and comment, and the domain checks the attachment on the pinned Zotero instance before sending one batch. The result reports a verdict for every selected page. The PDF browser smoke checks backward, multiline selection across rotated pages. The host and local annotation specs check both approvals, the native payload, and partial or ambiguous receipts.

Reader merges annotation tag changes with the saved tag set under the same version as scalar edits, preserving retained tag types. Deletion confirms the selected annotation in the tab and uses Zotero's versioned single-item DELETE after both host approvals. When approval requires an active turn, Reader keeps the pending edit or deletion available. A stale version refreshes the list. An ambiguous confirmation carries the annotation ref so the user can reconcile it in Zotero. The Local API annotation tests check the version header, tag retention, and ambiguous deletion.

Canceling an annotation edit or deletion returns focus to its trigger in the originating Reader view while that view remains visible. `tests/client/reader/ReaderTab.annotations.spec.tsx` covers two views of the same attachment, including when the originating tab is hidden or closed before the focus callback runs.

Reader creates linked notes through core’s Markdown note pipeline. After approval, edits verify the UI-observed version on the pinned Zotero instance. The writer applies escaped text and optional bold, italic, or code formatting only at parsed source offsets in ordinary note blocks. A formatted subrange uses half-open UTF-16 offsets within the submitted run. The writer checks both boundaries before escaping and wrapping the selected text. This preserves surrounding Zotero HTML, citation attributes, annotation links, and images. The domain reads the saved note to verify its version and contents. Permanent deletion uses the same version check and a single-item DELETE. The editor checkpoints drafts in browser session storage by DSH session and server-qualified item. When storage denies a write, the open browser tab holds up to 16 fallback records, including clear markers that shadow older stored drafts. A draft from another Zotero version or an unverified submission opens read-only so the user can recover its text. A verified save clears the draft. `tests/local/write/reader-notes.spec.ts` verifies markup and read-back. The host and client note tests cover approval, conflict handling, and draft recovery.

Every write goes through the unified `ctx.zotero` seam: capability gate → read-only preflight → `ctx.approval.request` → plan-review card → Local API. Zotero consumes a one-time key during authorization, so the key is held exclusively from authorization through send; the whole read-modify-write cycle has a 15-minute budget covering queueing and authorization. A batch carries at most 50 objects and writes children before parents according to dependency layers; every receipt must prove index, identity, version, and all submitted fields. A missing or contradictory receipt returns `committed-unverified` and is never retried.

Notes compare HTML structure and accept only the verified Zotero wrapper, control-character cleanup, and HTML-parse equivalence; tags and collections compare as sets; personal-library relation URIs normalize to local identity. Collections, notes, and collection membership run `preflightWrite` to exclude known invalid targets before approval and re-read current state before writing. Free-text feedback on the plan card always declines the current write, even when the same answer also selects Apply. Saved searches are re-read after PATCH and checked for name, all conditions, and version.

`src/shell-write-detector.ts` turns recognized Local API write commands seen at `tools/pre-execute` into one pre-run approval. It covers only recognized command shapes; a request assembled at runtime is a known blind spot.

### Scholarly Retrieval

Mounting the component is the authorization. Index searches reach only `SCHOLARLY_HOSTS`; the open-access PDF arm that leaves the allowlist also passes the public-address gate. Fusion prefers strong identifiers (formal DOI, PMID, PMCID, arXiv ID); without a shared identifier, records merge only when the title token set is identical, the first author's surname and initials match, and both years are within one. Version relations merge into one record, the primary record prefers the formal version, version metadata stays in `ScholarlyPaper.versions`, and retraction propagates only within the same record.

Citation tools parse the response by requested format and verify the DOI: CSL-JSON needs a parseable record with a non-empty title and matching DOI; BibTeX needs an `@type{...}` structure and matching `doi`; RIS needs `TY`/`ER`/`DO`; `text` rejects empty bodies and obvious HTML error pages. An HTTP 2xx is not evidence of citation validity. `scholarly_verify` compares a bare DOI only against identifier resolution and retraction status; a complete reference compares only the fields it supplies, and absent fields are `not-compared`.

### Document Parsing

A parse target is either `{kind:'attachment',ref}` or `{kind:'url',url}`: a specific child or top-level PDF attachment, or a public PDF URL. Host paths, session files, raw bytes, and unknown fields are rejected. A request carries the session and a per-operation idempotency key, and the mode is fixed to the committed configuration snapshot. The enrichment endpoint runs only after user confirmation; upload requires the component to be enabled, a specific target, a remote-action grant, and a session check. Scholarly authorization or `allowUrlPdfRead` never grants upload.

Parse jobs use real `ctx.jobs` and share a `ParseFlight` by source, mode, and generation; each session can read or cancel only its own job. Cancellation is synchronous and idempotent, and `done` settles only after real cleanup. Closing the interface releases only the observer; explicit cancellation, session close, or unmount withdraws the waiter, and the shared parse aborts when the last waiter leaves. A reparse uses a new generation and switches the source pointer atomically only after the new artifact is complete; failure or cancellation keeps the previous valid artifact.

A parse receipt carries target identity, generation, mode, cached or new artifact, fingerprint, artifact revision, available page count, character count, and a bounded preview. Error messages first lose URLs, paths, and credentials and are then capped at 256 characters. Receipts never expose host paths, signed URLs, tokens, or body logs. Session operation receipts and generation pointers live in a separate `$DSH_HOME/zotero-receipts/parse-jobs/`, independent of the artifact directory; task records expire 24 hours after upload, and poll exhaustion clears resumable state. The panel-parse completion-notice workaround is DN-1 in `development-notes.md`.

### Literature Trail

The trail shows only read and export facts produced in the current session; it records no writes and no out-of-library literature. Projection state version is 3 and holds only the chunked ledger; a strict schema rejects extra fields from older versions, and the host rebuilds by replaying session events. Running, failed, and stopped calls count only toward `operations`; ref-less searches additionally count toward `searchOperations`. Search episodes fold by identity; the client materializes `evidenceMatch` from the status probe. The host retains complete events and bodies; paging never truncates their content.

## State, Storage, and Consistency

### Parsed Artifacts

Artifact directories live at `<outputDir>/<sha256>/` with `full.md`, `meta.json` (plus `content_list.json` for the precise API), and `images/` referenced by the Markdown; `meta.json` is written last as the commit marker. The source index at `sources/index.json` records the latest artifact and source stamp by the canonical source's SHA-256. The artifact directory and source index are two independent writes, so listing merges both views by cacheKey and deduplicates, recognizing orphan directories, dangling index records, and corrupt meta.

Deletion first takes exclusive ownership of the generation, aborts and waits for related parses to settle, then clears every alias key, task file, that generation's parse receipts, and in-memory records, and invalidates read leases bound to the artifact before cleanup. When the first orphan has not yet created `sources/`, deletion still creates the index lock directory safely. The complete canonical URL lives only on host disk and in `meta.json.sourceUrl` to restore an orphan target; it never enters identity, receipts, wire results, or display fields.

The artifact root must be a POSIX directory owned by the current user and not writable by group or others; ancestors must be owned by the current user or root, or carry sticky protection, and any ancestor writable by others must be sticky; new directories use 0700. Commit metadata records SHA-256 digests for Markdown, the optional content list, and every image; every read verifies digests and byte/character bounds; an older artifact without digests is explicitly invalid. Windows ACLs are not judged by POSIX uid/mode.

ZIP handling first verifies agreement among the directory, local headers, data descriptors, and entry ranges, then inflates only selected text and referenced images. Native deflate `maxOutputLength` caps actual output; output length, consumed compressed length, and CRC must all match; originalSize is metadata only. The Worker has heap/stack limits and a 30-second deadline; cancellation waits for exit before releasing the slot; unreferenced entries still count against directory and range budgets and are not inflated.

### Write Generation and Cache

`ParsedArtifactStore` is memoized per resolved root (one instance per root); the inventory (directory enumeration plus one `metaFor` per cacheKey) is cached by write generation. Every write attempt, including a failed one, first calls `touch()` to advance the generation and invalidate the cache; every new store write method must do the same. The source index is read per call and never cached; an index I/O failure must surface.

Committed MinerU Markdown is authoritative for the derived parsed index. Each output directory holds its own SQLite database at `<outputDir>/index.db`. The FTS5 partition has a stable name so it remains usable if the output directory moves. WAL transactions publish complete generations. Parse commits and discards update the index, and a library or collection search backfills existing artifacts. Current Zotero instance, active source and collection membership constrain candidates before ranking. Returned offsets address verified Markdown. Restricted scopes compute length and frequency statistics from their authorized documents. Single-paper evidence uses in-memory BM25 and optional local ONNX. The parsed index recalls candidates across documents. `tests/host/enrichment-parsed-index.spec.ts` exercises generations, scope and text spans against real SQLite.

`lookupArtifact` hits the read-through cache by `(artifactId, contentFingerprint, parseGeneration, store.writes)`; on a miss it reads only the source index and `meta.json`. An artifactId addresses a local artifact, so a URL-derived document stays readable offline after parsing, and deleting the local attachment does not invalidate it. `lookup` for an item ref still performs one stat/HEAD because it reads Zotero's index text.

### Result Delivery and Receipts

An over-budget result is stored in full as an attachment with a bounded receipt; a storage failure fails explicitly, and a background job never replaces the body with the complete text or truncates it. Receipts retain the latest 128 deliveries per session and 1,024 globally by publication time, evicted by the call/job pair; deleting a receipt does not delete the host-owned session file. A corrupt receipt is backed up in isolation.

Parsed search keeps evidence refs in the durable receipt and session presentation metadata. The model-facing attachment notice omits previews first and evidence refs next as needed to fit the inline budget, marking omissions with `detailOmitted`. `tests/host/result-delivery.spec.ts` checks the attachment, receipt, session metadata, and notice size for the same result.

Browse cards keep at most 20 full prefix rows and count JSON separators inside a 6 KiB row budget; real paging and return counts are preserved, and `omitted` names rows not shown. Writes check scalars before planning and before service approval and cap HTTP encoding at 1 MiB without truncating the body. A foreground promotion race publishes one attachment; an unpromoted candidate does not copy its body into the job outcome. Unmount closes new admission and waits at most 5 seconds; work already entering publication keeps its domain handle until settlement.

### Trail Persistent State

Projection state stores only facts that participate in folding; the strict version-3 schema rejects extra fields from older versions, and the host rebuilds by replaying session events. Inherited events fold like ordinary events. Retrieval tools reject `includeTrashed`, so trail occurrences never claim that capability. Production reads use only the incremental `SourceWorkspaceIndex`; tests read through the real projection instead of keeping a second full-replay implementation.

### External Cache

The scholarly fulltext cache stores one JSON body per key and keeps eight index entries in memory; reads are `hit`, `miss`, or `corrupt`, and corrupt entries are evicted and recorded. Eviction invalidates the memory entry immediately; a disk cleanup failure becomes an issue on the current read; a cold read accepts only a snapshot that no write or eviction interleaved, so late bytes cannot reenter memory.

`include:["fulltext"]` reads the current fulltext index list (`/fulltext?since=0`) and returns each attachment's fulltext index version. It is not a library-transaction cursor increment and cannot tell when an attachment was reindexed. Trash fallback derivation yields items only when both lists are complete; a partial input is never treated as proof of deletion.

## Concurrency, Resources, and Isolation

The transport holds a global in-flight gate (`maxInFlightRequests`, default 8) across transport rebuilds: shrinking first drains admitted requests, and growth releases waiters in order. Response reads are capped by `maxResponseBytes`; timeouts combine a fused deadline with the caller's cancellation signal.

Document reads use `documentArtifact`: `open` carries a client UUID `requestId`, binds the real peer, session, original agent, and the store fixed at open time, and returns a read lease, image manifest, and first body block; `page`/`image` read a fixed version by lease; `release` is idempotent by requestId. A body block holds at most 65,536 characters; authorization is checked before reading and after asynchronous I/O. A source generation change or directory switch does not affect an existing snapshot; because a browserPeer can be shared across browser connections, page close is covered by explicit release, a one-shot deadline, and resource budgets, not by `peer.signal` alone.

The ZIP worker inflates, analyzes references, and validates content lists in a separate Worker; the parent verifies a closed message set, and persistence receives only normalized payloads; production runs `lib/enrichment/zip-worker.js`. Archive admission concurrency and queue limits come live from the `artifactReader` configuration; `ParseFlight` must receive the live policy, because constructing it with the default policy silently disables both settings.

Local semantics: a ranking scope calls `admit()` before any source I/O, fixing the committed configuration, model target, and service generation, and releases in `finally`. Loading starts on that scope immediately, so a model switch after admission cannot move the read to another model. A model switch commits only after the new model loads; the old instance is released after the last scope and actual inference end; a resident model is recycled after `semanticIdleTimeoutMs` (default ten minutes) without requests.

Each model owns an independent worker: opening has a 180-second deadline, a single inference request has 120 seconds, and a timeout terminates the actual thread and waits for exit before the next model opens; caller cancellation ends only that caller's wait. Returned vectors are checked per batch for count, Float32 type, dimensions, and finite values; a terminated resident serves no new scope, and a new request reopens from disk. Bundle verification, tokenizer, and ONNX session belong to the worker: manifest read is bounded at 64 KiB, symlinks are refused, and every file is checked by SHA-256. Queries and rewrites are capped at 2,000 characters; embedding text with its prefix is capped at 131,072 characters; a padded batch splits at 32,768 tokens, keeps every row, and encodes each row once; each generation's vector cache allows one inference batch in flight and at most 16,384 items / 64 MiB across requests.

A deterministic missing or corrupt bundle caches at most 16 identity snapshots; reuse re-compares the canonical directory, catalog fingerprint, directory, manifest, and every pinned file's identity (dev/ino/size/mtime/ctime or absence). Path-safety refusals, I/O, runtime, cancellation, and timeouts are not cached; ranking failure never falls back to lexical results.

## Security and Trust Boundaries

The Local API accepts only loopback addresses (`127.0.0.1`, `localhost`, `::1`), pins API version 3, verifies instance identity with `Zotero-Server-ID`, strictly refuses redirects, and caps response reads with `maxResponseBytes`.

External egress checks names against the allowlist and permits only ports 80/443 (an explicit spelling equals the default port). The open-access PDF arm outside the allowlist also resolves the host and rejects any non-public unicast address (including NAT64/IPv4-mapped embeddings), pins the verified address into the undici connection, and re-runs the lexical and resolution gates on every redirect hop. The fake-IP exception applies only to reviewed allowlist hosts over HTTPS, HTTPS public PDFs, and HTTPS MinerU; plain HTTP, URL PDF, and model downloads still require a real public address. Proxy routing and address pinning are mutually exclusive, and external egress uses `publicFetch` from one undici copy; the workaround and its exit condition are DN-13 in `development-notes.md`.

The MinerU API host is fixed to `mineru.net`, and `Authorization` goes only there; signed uploads, result CDNs, and cache HEADs carry no credential. Signed uploads add no headers; non-2xx bodies are bounded and URL-redacted. Phase limits include a 30-minute total budget, 900 polls, 60 seconds for submit/poll, 20 minutes for upload, 10 minutes for result download, 20 minutes for source transfer, and 15 seconds for HEAD; task records expire 24 hours after upload.

URL PDF reading is separately authorized by `library.allowUrlPdfRead`; downloads enforce per-hop redirects, HTTPS downgrade refusal, type, PDF signature, 32 MiB, 60 seconds, and two concurrent reads; revocation cancels active requests. The browser retains only the source attachment ref, and a restored reader tab downloads again through explicit reload.

Model downloads allow only the fixed seed hosts, per-revision URLs, re-validated redirects, a byte cap, and SHA-256 verification; the host path has no proxy, and the CLI supports `--proxy`. Parsed-page remote images become plain links before display; only local images shipped with the artifact render through controlled Blob URLs; examples inside code blocks are untouched. The upstream renderer accepts remote images before calling pathImages, so the refusal policy runs at the local syntax-tree stage.

Credentials: scholarly and MinerU tokens are `ctx.credentials` references resolved per call; an invalid reference, missing service, or empty or malformed value fails closed (`ZOTERO_SCHOLARLY_CREDENTIAL_UNRESOLVED`, `ZOTERO_SCHOLARLY_CREDENTIALS_UNAVAILABLE`, `ZOTERO_ENRICHMENT_CREDENTIAL_UNRESOLVED`) and never downgrades to anonymous or free. The upstream `resolveCredentialRef` falls back to the launch environment when no credentials service is mounted, so this repository keeps its local per-call resolution wiring and a missing service stays a failure. The Zotero write grant lives in `dsh-credentials`, never in plugin configuration.

## Client-Host Contracts and Surfaces

Four Typert services register endpoints in the `zotero` wire namespace. `ZoteroRuntime` handles `status`, `resolveAttachment`, `diagnostics`, `reportClientError`, `openProtocol`, `revokeWriteGrant`, and `sourcePage`. `ZoteroLibraryService` handles `browse`, `collectionPath`, `search`, `item`, `childPage`, `export`, `write`, `readUrlPdf`, `releaseUrlPdf`, `journalMetrics`, and `refreshJournalMetrics`. `ReaderService` handles `readerTranslate`, `readerSuggestAnnotation`, `readerDetails`, `readerNote`, `readerWriteNote`, `readerAnnotations`, `readerCreateAnnotations`, `readerUpdateAnnotation`, and `readerDeleteAnnotation`. `EnrichmentService` handles explicit parsing, artifact receipts, parsed-document management, and semantic-model management. `domainCall` preserves domain error codes and distinguishes cancellation from Gateway errors. Only the exact `gateway/service-unavailable` code means the component is absent.

The Literature panel and Reader share the Library component’s journal metrics Remote and accepted settings. After Zotero items load, the panel deduplicates and queries journal names on the current page when list candidates are configured. When detail fields are configured, the selected item has an independent, higher-priority lookup. Reader requests that lookup only when the user clicks the lookup button on a journal article’s details, and cancels it when the details close or access is revoked. `tests/client/reader/ReaderDetails.spec.tsx` checks the request and revocation. The host resolves the credential while the separate permission is on, shares in-flight lookups for the same journal, spaces request starts at least 500 ms apart, and honors EasyScholar's Retry-After cooldown. Successful lookups are written atomically to a host cache capped at 512 entries, indexed by a digest of the key and normalized journal name. Each record contains the normalized journal name, metrics, and lookup time. Results are reused for six hours. The settings action `refreshJournalMetrics` uses the same queue to update all saved journals for the active key and reports the number refreshed and any failure. Failed refreshes preserve saved records. Cancelling the last waiting caller aborts the lookup. Revoking permission or replacing the key invalidates the in-memory generation. Queries send the journal name and key to one fixed HTTPS endpoint and do not follow redirects. `tests/host/library/journal-metrics-cache.spec.ts` covers reuse after restart, credential isolation, and fallback on refresh failure.

The host supplements `officialRank.all` with fields found only in `officialRank.select`. A null `customRank` represents an empty set of custom ratings. A successful EasyScholar response may set both `officialRank.all` and `officialRank.select` to `null`. When both are empty and there are no custom matches, the host caches an empty successful result. Actual errors send only a category to the client, since raw responses and connection errors can include the key.

EasyScholar returns `40006` when the key reaches its cumulative query limit. The host settles pending queries for that key, keeps cached results, and returns the quota status for the next minute. Replacing the key allows queries to resume immediately.

The browser starts with `lib/client.js`. Reader tabs and completed turns with Reader citations load the Reader UI. Opening a PDF loads its runtime and Worker. Every surface registers after `remote.zotero` mounts. `whileServed('library')` gates the panel, its config row and its requests. Shared DTOs avoid host execution imports and fulltext spill implementations. The host entry owns the write approval context and job kinds. The browser compiles separately with no Node globals. The declaration gate checks the TypeScript-resolved file list and rejects host jobs, tools and agent root entries.

Reader text tabs and parsed-document tabs apply the Markdown image policy in their deferred UI chunks before handing text to the host renderer. The startup bundle keeps resource preparation and access checks. The parsed-document loader and image specs check chunk failure and confirm that remote figures render as links without issuing image requests.

An open ordinary conversation can edit local Reader drafts and request model excerpts between turns. The host resolves the Agent for the owning session and rechecks session access after resolution. Native writes require an open Harness turn to record the approval decision, plus session approval and plan review. Direct Reader writes omit the optional tool call ID when there is no invocation to identify, so the gateway can serialize the approval request. Reader tabs remain mounted while the Harness plan preview has focus and cancel their work when closed. Host specs verify the approval payload and revocation. The packed Web smoke approves once and declines the plan, then checks that Zotero remains unchanged.

Surfaces include the literature trail (`conversation.view`, id `zotero`, order 30), the literature panel (`sidebarRightTabs` + `sidebar.right.pane.tab`), tool cards (`tool.call.toolview`), settings and plugin management (`plugins.bundle.config` and peers), context menus (`contextMenus`), and document preview actions (`sidebar.right.tab.document.actions` / `.unpreviewable`). The panel's data plane, access gates, session binding, navigation state, and write entry follow `src/client/**`; layout tiers live in `library.module.css`, and user-visible behavior lives in `features.md`.

Disclosure: the client shows a notice while a component is served and this browser has not acknowledged the disclosure; the acknowledgement is kept per browser, and observing the component off revokes it so a later serve discloses again. When storage fails, session state carries acceptance and revocation. Scholarly and enrichment each own one disclosure, shown by a shared arbiter in registration order rather than as stacked modals.

Opening a local PDF from the panel goes through the right sidebar's `openResource`; when no session surface is mounted, the upstream refusal is prose only, so the client translates `NO_SESSION_SURFACE_REFUSAL` into a panel message; the workaround is DN-9 in `development-notes.md`.

The parsed-document manager page loads `listParsedDocuments` in windows; rows open, reparse, or delete by artifactId, deletion asks for confirmation and refreshes open parsed-result tabs. A parsed-result page's address contains only the session and attachment ref (URL sources use artifactId); the host `useResource` prepares the complete Markdown and figures and publishes once, keeping the previous document readable during a refresh. A parse receipt refreshes open pages in the current session: the client confirms the source's current index with a lease-free `meta`, refreshes attachment pages in place, replaces artifact pages through `replaceTab`, and clears old selections and Blob URLs on a switch.

FTS5 coverage checks the active partition against committed artifacts by artifactId, sourceId, generation, and Markdown digest. A rebuild job tokenizes one document at a time into a private staging database. Under the artifact publication lock it checks generations and digests again, then replaces the partition data and FTS5 table in one SQLite transaction. Cancellation, artifact drift, or rebuild failure preserves the last committed partition. The visible manager observes progress while a job is active.

Batch parsing reads PDF attachment metadata across all pages, looks up parent items by key in batches under the same Zotero instance and library version, and saves an expiring catalog snapshot for the session. Confirmation binds the catalog, selection, and operation ID. Selecting all means every PDF in the snapshot minus explicit exclusions. The host queue admits one existing parse job at a time and uses the same generation, source lock, receipt, and authorization checks as individual parsing. Cancellation releases the current batch waiter and skips attachments still queued. The batch summary follows the host and session lifetime. Individual receipts use the existing durable store.

The explain/ask card asks the model to read the whole bounded document once with `mode="fulltext"` and `complete=true`; a `spillRef` is read through the host `read`/`grep`, an inline result is already complete, and only an unavailable complete read falls back to a window chain. The answer then explains the passage in interface language in labeled blocks (one-sentence thesis, place in the argument, substantive content, scope and evidence), verifying quotations and reference details before stating them. The active interface language exists only in the browser, so the client writes its name into the prompt; the upstream gap's patch is DN-49 in `development-notes.md`.

Navigation: `useLibraryNavigation` owns continuous prefixes, library versions, in-flight deduplication, and at most four navigation tasks; storage uses v3 keys and formats, isolated by instance and session, keeping only state and view markers. `collectionPath({library, ref, libraryVersion})` goes through `ctx.zoteroLibrary` → `ctx.zotero` → Local Provider under the browse capability gate; it returns the real collection rows from root to target plus the library version and verifies the version with a light listing read at the end. Collection and saved-search pages must carry a valid `Last-Modified-Version`; both codecs reject a missing version.

Diagnostics: a 500-entry in-process ring buffer records HTTP requests, tool calls, job states, configuration changes, write gates, shell-write detections, connection probes, and degradations; `tool.result` is recorded when the result is published, warn for failures with the stable `errorCode`, and `ms` spans `tools/execute` entry to publication. Request lines are off by default; enabling diagnostics records them and merges consecutive identical entries. `zotero/diagnostics` returns a reverse-chronological snapshot; the frontend card polls only while diagnostics are enabled and the panel is visible. Records stay in memory, never touch disk, and send no telemetry; HTTP records contain no response body or literature text.

## Design Boundaries

The library is read-only by default; `writeEnabled` permits writes only to the personal library (`zotero://user/0/`). Local requests are restricted to loopback and refuse redirects; external scholarly retrieval is authorized by scholarly, user-initiated URL PDF reading is authorized independently by the library panel, and MinerU requests come only from an enrichment parse the user explicitly submits for a specific target; local semantics never contact MinerU, and model downloads are initiated independently.

There are no resident polling daemons or telemetry collectors; long-running core, scholarly, and enrichment work uses `ctx.jobs`. Background parsing and downloads abort and wait for cleanup on unmount, and admitted foreground read scopes drain before release. The literature trail shows only read and export facts from the current session, records no writes, and excludes out-of-library literature; Trash is a panel-only scope that model tool schemas do not expose.
